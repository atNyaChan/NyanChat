# Nyanw 版本改动记录

## Agent 协作约定
- `AGENTS.md` 要求 Agent 在每次代码、资源或配置修改后同步维护本文件。
- 编辑本文件前先从头到尾阅读一次，不要只是往最后添加信息，也不要只使用 grep 简略阅读。
- 修改完成后要静态检查本次改动涉及的未引用组件，并删除未引用的翻译资源字符串，并使得各翻译资源与英文源文件同步。
- 禁止 Agent 自行执行编译、构建、测试或 Lint；相关验证由维护者手动完成。

## 聊天与消息
### 词数及生成统计
- 设置里的“显示 Token 数等统计信息”改为三档选择：关闭 / 简洁 / 详细（默认详细）。持久化上沿用原 `showTokenUsage` 布尔字段表示是否关闭，新增 `detailedTokenUsage` 区分简洁与详细。“简洁”跟上游打开 token 统计时的行为一致，“详细”在下面具体说明。
- 相邻 ASCII 英文字母合计为一个词；其他 ASCII 符号、空格、CJK 字符和 emoji 等每个 Unicode 码点各计一个词。
- 用户消息的操作按钮行左侧显示词数。
- 流式回复期间每 100ms 更新词数（包含正文和思考过程）、已用时间、词/秒（尚未调用工具时）及生成中的思考词数。
- 生成完成后助手统计变为两行：第一行显示词数、时间（、词/秒）、`round #n`（表示该消息是当前会话中第 n 条助手消息）、`, {n} steps`（仅当该消息请求模型的步数大于 1 时追加），第二行显示输入（缓存 token）、输出（、token/秒）及费用（如果设置了模型单价）。未调用工具或消息记录了 `generationTimeMs`（此时耗时不含工具执行与审批等待）时显示 `word/s` 和 `tok/s`。
- 消息用时不足 150ms 时不显示 `word/s` 和 `tok/s`，避免展示失真的瞬时速度。
- 没有 `generationTimeMs` 的旧的含多次模型调用（多轮工具调用）的助手消息第二行最前面标注 `Last LLM Call:` 且不显示速度；若有 `generationTimeMs` 则在第二行最前面标注 `Total:`。
- 点击统计只切换精确数字和 `12.3K` 一类的缩写；仅数量超过 `10000` 时才采用缩写，并且无论数量多大都只使用 `K`。
- 模型 id 为空的助手消息（即为手动编辑的消息）只显示词数，并标注 ` (edited)`。
- 手动编辑的消息中的思考块只显示“思考”，自然生成且带有用量信息的零耗时思考仍显示“思考了 0.0 秒”。
- 输入框加号左侧分两行显示{当前输入词数、下一次请求总词数（开启“回传思考”时计入历史思考内容）}、{附件与可供模型使用的工具数量（含内置工具）}；第二行按实际存在的项目显示文件、工具图标及数量，两行右对齐并整体垂直居中。
- 编辑历史消息时输入框统计只覆盖被编辑消息及其之前的内容。
- 编辑消息时的“编辑中”卡片显示在输入框最上方（附件列表之上）。
- 输入框中的可解析文本文件会在附件框外侧右边显示文件正文词数，计入下一次请求总词数，不计入附件数；当前输入词数只统计直接输入的文本，不重复计算附件词数。
- 输入框获得焦点时构建并缓存系统提示、记忆、工具提示及转换后的既有历史消息；显示的总词数直接为缓存上下文词数加当前草稿词数。
- 组装系统提示时只为非空的记忆段与工具 `systemPrompt` 预留分隔换行；没有内容的工具（如 `workspace_*`）不再各留一个空行，避免系统提示词中出现大段空白。
- 正在生成消息（发送按钮被取消键取代）期间跳过下一次请求总词数与工具数的统计（不只是隐藏显示），生成完成后自动重新统计并刷新显示。
- 操作消息树（删除消息或切换消息分支）后重新统计下一次请求总词数、工具数与文件数。
- 点击输入框旁的加号打开面板修改设置会实时刷新上下文统计值。
- 用户消息中的可解析文本文件左侧显示灰色文件正文词数；只统计解析出的正文，不包含文件名及请求转换时加入的上传文件标签或包装文字。
- 键盘未弹出且没有草稿或附件时隐藏统计；展开加号面板时仍显示统计。
- 统计数值沿用消息统计的 `K` 缩写规则；关闭“显示 Token 数等统计信息”设置时不显示也不计算。
- 用户消息时间位于词数统计左侧（关闭统计时仍占据该位置），用户与助手消息时间均沿用词数统计颜色；今天和昨天的消息分别以“今天”或“昨天”代替日期，其余日期使用 `yyyy/MM/dd`，后面均保留 `HH:mm` 时间。
- 请求转换时把解析出的上传文件正文放在用户消息文本之后（同一输入框中存在多个文件时保持文件原有顺序），不再放到用户提问之前；未解析的图片等附件同样保持在用户消息之后。

### 思考块
- 带签名或加密内容的思考同样允许编辑，但点击“编辑思维过程”会先弹出提示框：标题“编辑思维过程”、正文“该回复含有加密思考链，编辑后将丢弃加密思考内容。”、按钮“取消 / 仍然编辑”；确认后编辑，落库的思考不再带原来的 metadata（加密内容被丢弃）。
- 新增设置“解析中途思考”（默认：开启），开启时消息开头以外的 `<think>` 标签也会被解析为思考块。仅作用于流式生成，不影响手动编辑的消息。
- 思考完成并展开思考块后，顶部右侧显示思考词数和复制按钮（点击即可复制思考 Markdown 原文）。
- 展开或收起思考与工具步骤时，标题行的按压反馈左右各保留 4dp 空白，圆角半径比思考块卡片小 4dp（内缩距离）以保持共圆心。
- 设置里的“生成时显示思考”可以选“收起”、“预览”和“展开”。思考中点击思考块标题即可在收起与展开（设置值=“收起”）或预览与展开（设置值=“预览/展开”）之间切换。
- 渲染思考块时去掉思考块结尾的换行，避免末尾残留多余空行。
- 缩短思考块内文字与思考块下边缘的间距。
- 记住思考块的展开/收起状态：思考块滚出屏幕被列表回收后再滚回来，仍保持原来的展开状态。
- 思考/工具时间线的连线的最后一步下方仍保留向下连线，并距容器底部 16dp 收尾。

### 空白消息
- 允许发送仅包含空格等空白字符的消息。真正的空字符串仍不能作为单独消息发送。
- 纯空白用户消息使用不可见占位符维持正常气泡行高；该占位符仅用于显示，不改变保存或发送的原始内容。
- API 生成流正常结束（收到发送完成事件）、回复长度确实为 0 时保留空助手消息；失败和取消仍移除空占位消息。
- 所有消息（含零长度、非末尾及生成中的助手消息）的底部操作按钮栏（复制/重试等）始终显示。

### 消息的模型来源显示
- 手动编辑助手消息产生的新版本**不继承**原消息的模型 UUID 与模型名称快照，编辑过的助手消息仍按“模型 UUID 为空的手动编辑消息”处理（只显示词数并标注 ` (edited)`、思考块只显示“思考”，不显示模型图标与模型名称）。
- 既查不到模型、消息上又没有快照时，退回显示消息记录的模型 UUID（括号包裹，如 `(00000000-0000-0000-0000-000000000001)`）作为模型名称，而不是隐藏整个显示；Android、聊天图片导出与 Web 界面头像行行为一致，Android 端的模型图标此时为空白占位。
- 消息三点菜单底部的模型名称（或模型被删除后且没有快照时退回显示括号包裹的 UUID）为可点击链接，点击后关闭菜单并跳转到搜索页按该模型筛选消息；回退显示时括号为普通文本，仅括号内的 UUID 为可点击链接，并使用等宽字体。

### 模型价格
- 每个提供商的每个模型均可选中“设置价格”。
- 支持填写输入、输出、缓存读取、缓存写入价格，单位为美元/百万 token（输入/输出一行、缓存读取/写入一行）。
- 价格设置默认关闭，旧模型数据因字段具有默认值而保持兼容。
- 未出现缓存读取时，费用计算为 `输入价格 × 输入 token + 输出价格 × 输出 token`。
- 出现缓存读取时，不使用普通输入价格，费用计算为：
	```text
	缓存写入价格 ×（输入 token - 缓存读取 token）
	+ 缓存读取价格 × 缓存读取 token
	+ 输出价格 × 输出 token
	```
- 开启模型价格设置后，在四个价格输入框下方直接显示无缓存读取与有缓存读取两种计算公式。

### 侧栏
#### 搜索消息
- 从侧栏“搜索消息”入口进入搜索页时，自动从底部弹出“搜索条件”抽屉（通过带模型 ID 的外部跳转（模型详情页、消息三点菜单中的模型名链接）进入时不自动弹出）。
- 搜索页右上角提供三点按钮，点击即可从底部弹出“搜索条件”抽屉；抽屉内容为一个 `CardGroup`，自上而下依次为：搜索内容输入框（`OutlinedTextField` “搜索文本”）、“匹配方式”（“标题/原文/模糊”三段选择）、“排序方式”（“最新/最旧/最相关”三段选择）、“搜索范围”（“全部助手/当前助手”两段选择）、“模型…”行与“附件”下拉行，底部为取消/确认。
- 确认后一次性提交全部条件并执行搜索，所有搜索条件同时生效。
- “模型…”行点击后弹出“全部/现有的模型/已被删除的模型/手动编辑的消息”四个选项，选择后在该行右侧以灰色文字显示当前选择项；“附件”下拉框提供“全部/没有附件/存在附件/附件被删除”选项。“已被删除的模型”列表项及其选中后回显的模型 ID 使用等宽字体。
- “现有的模型”打开模型列表时，只列出聊天记录中出现过（消息带该模型 ID）且仍存在于设置中的模型；未在聊天记录出现过的已配置模型不显示，模型所属提供商即使被禁用也照常显示。
- 默认使用原文匹配并记住用户选择（搜索方式与排序写入偏好设置）。原文匹配使用区分大小写的连续字符串包含判断；模糊搜索按空格拆分关键词，要求各段在消息中依次且全部出现，且匹配不区分大小写，例如 `你 好` 可匹配“你真好”，`S r h` 可匹配 `search`。
- 排序选项“最相关”仅在模糊搜索时出现，非模糊搜索时该项整项不显示，从模糊切回其他模式会自动改为“最新”。
- 模糊搜索选择并高亮消息中，各空格分段按顺序出现且间隔字符总数最少的一组完整匹配；按相关性排序时优先显示总间隔更少的结果，相同则按消息时间从新到旧。
- 预览从首段所在行延伸到末段所在行，匹配相隔较远时自动包含中间全部行。
- 新版搜索统一读写独立的普通表 `message_search_cache`，不扫描消息 JSON，并移除 Jieba 查询与词典资源。旧名 `message_fts` 保留为空的 `simple` FTS5 兼容表，旧版会忽略新缓存表，导回旧版后可手动重建旧索引。仅当没有模型/附件/手动编辑筛选时走该缓存快速路径；叠加任一消息级筛选时改为扫描消息 JSON 在内存中逐条过滤。
- 消息搜索缓存写入完整文本，不再将每条消息截断到 10,000 字。
- 新版打开数据库时若发现旧表存在条目，会先清空旧表，再与页面手动重建共用同一实现，从原始会话及消息记录全量重建新缓存，两个缓存表的旧内容都不会作为重建来源。
- 侧栏入口与搜索页标题统一复用“搜索消息”文案。
- 消息搜索在标题同一行显示“xx 个结果”；滚动收起标题与返回键同行后，“xx 个结果”改到“搜索消息”下一行显示。
- 搜索结果每页 20 条，超过一页时在结果列表上方提供首页、上一页、页码输入、下一页和末页控件。翻页后搜索结果列表自动滚回最前面。
- 重建搜索索引时清空页面内容，仅保留标题栏及右上角按钮，并在内容区域中央显示圆形加载指示器。
- 每条搜索结果底部的时间后同一行以“ · ”追加会话来源，例如 `{日期} · Assistant/Folder`；会话未归入文件夹时只显示助手名。
- 消息级搜索结果显示与排序均使用消息自身的生成时间（`UIMessage.createdAt`），不再使用对话的最后更新时间；“仅匹配标题”的结果仍使用对话更新时间。`message_search_cache` 新增 `message_at` 列存放消息时间，原 `update_at` 列保留并继续写入对话时间以兼容旧版；打开旧数据库时若缺少 `message_at` 列会补列并全量重建；若整表 `message_at` 全为空（例如数据库被旧版重建过索引），打开时也会静默全量重建补回消息时间。

### 备份与恢复
#### 聊天附件
- 消息里的附件 url 以相对 `filesDir` 的路径落盘（`upload/<sha256>`），不再写入带包名的绝对 `file://` 路径；内存中的 `UIMessage` 仍持有当前安装的绝对 url，由 `data/files/LocalFileUrls` 在 `ConversationRepository` 的读写边界统一折叠与展开。落盘值只可能是相对路径。
- 聊天附件使用内容寻址存储：实体直接放在 `filesDir/upload` 下，以内容 sha256 命名，相同内容只落一份。
- 输入框/消息队列里的附件先放在 `cacheDir/upload_tmp` 临时目录（进程内有效、不写登记表、不参与 CAS）；展示名、来源 MIME 与写入时算好的 sha256（边写边算，提交时不再重读整份文件）只保存在进程内的内存表里。从输入框/队列移除或启动应用时直接删除临时文件，提交时若临时文件已消失则丢弃该附件。
- 新增附件时按内容 sha256 对同一个输入框去重：聊天附件选择器（拍照/相册/视频/音频/文件/画板）、输入框粘贴和通过分享传入的文件都会先与输入框已有附件比较，重复的候选项直接丢弃并弹系统 Toast“此附件已添加”，保证一个输入框里不会出现两个相同内容的附件。
- 只有会话真正落库时才把临时附件提交成 CAS：按内容流式重命名到 `upload/<sha256>`（相同内容复用已有实体），展示名/MIME 随 `commitConversationFiles` 的返回值带出，透传给 `updateAttachmentIndex` 写成最终的 `message` 使用记录，再用提交后的 url 替换消息。
- 仓储落库前只做守卫：若仍扫到临时目录 url，说明调用方漏了提交，整段丢弃这些附件并记 warning，绝不把临时路径写进数据库。
- 同一份内容被再次带入时，若登记表里的 MIME 还是空值或 `application/octet-stream`，顺带用本次更具体的来源 MIME 补全。
- 附件登记信息保存在数据库 `managed_files_cas` 表（一个 sha256 一行）：`id`、`sha256`、`mime_type`、`size_bytes`、`usages`（数据库版本提升到 100）。`usages` 是 JSON 列表，每项为 `{type, filename, display_name, created_at, details}`：`filename` / `display_name` 是该次使用在旧版（RikkaHub 兼容）布局里对应的 `uuid.ext` 文件名与展示名，`created_at` 是该次使用的时间（`message` 时取消息时间）；`type` 为 `message` 时 `details` 为 `{conversationId, nodeId, messageId}`，`assistant_background` / `assistant_avatar` 时为 `{assistantId}`，`user_avatar` 时为空，`type` 为 `none` 表示这份内容没有任何使用，`details` 为空、`created_at` 记录落盘时间、`display_name` 记录最近一次带入的展示名。旧的 `managed_files` 表已被 `managed_files_cas` 取代。
- 每次设置落盘时若助手头像/聊天背景、用户头像发生变化，就重建这些内容的 `assistant_avatar` / `assistant_background` / `user_avatar` 使用记录；恢复备份后启动时也重建一次（平日启动不重建，设置变化已由落盘路径增量维护）。
- 启动时 `syncManagedFiles` 对齐磁盘与登记表：`upload` 下文件名不是 64 位小写十六进制 sha256 的（旧布局残留等）会按内容重新计算哈希并重命名为 `upload/<sha256>`（相同内容去重）后再补登记，文件名已是 sha256 的直接按名登记，避免把任意文件名当成内容哈希写进登记表。
- 一份内容只要还有真实 `message` / 设置类使用就不会保留 `none` 记录；反之只剩一条 `none` 记录。
- 所有读写 `managed_files_cas.usages` 的删除与清理都与索引更新共用同一互斥锁，避免并发下互相覆盖。
- 保存/删除会话只加载本次引用到的内容与该会话此前引用过的行；`FilesManager` 在 `usagesMutex` 内维护一份懒加载的 `conversationId -> sha256` 内存索引。
- `usages` JSON 解析失败时按消息库重建全表索引，重建后仍无法解析的内容保守保留（不删文件、不改写记录）。
- “存储管理”的设置主页描述固定显示为“{n} 个文件（{n} 个引用），{size} MiB”：文件数按 `upload` 下文件数计，引用数按 `usages` 里真实 `message` 条目数计，大小按 `byte / 1048576` 换算。

#### 新导出格式
- 新导出格式改为 `.tar`，文件命名为 `NyanChatBackup-yyyyMMdd-HHmmss.tar`：
	- 导出前使用 `VACUUM INTO` 生成包含已提交 WAL 数据的一致、独立快照，再压缩为单个 `.db` 文件。
	- 数据库导出一个 `rikka_hub.db.zst`，并使用 zstd 等级 9、长距离匹配窗口（`--long 27`）多线程压缩，再与 `settings.json`、`upload`、skills、fonts 等附件一起打入 tar。
	- 选择导出“工作区”时，在 `workspaces/` 下为所有非空工作区按根标识生成独立的 `{workspaceRoot}.tar.zst`；每个子归档复用单工作区导出实现，包含 Rootfs 及对应 `/workspace` 文件。恢复时会将两部分还原到对应工作区。
	- 导出普通文件时仍按内容去重：`upload`、`skills`、`fonts`、`media_creation` 中逐字节相同的文件只在 tar 内保留一份数据，其余条目写成指向首份数据的 TAR 硬链接，缩小备份体积。先用文件大小筛选，只有大小相同的文件才计算 SHA-256，大小唯一的文件不做哈希。其中 `upload`、`fonts` 只打包顶层文件，`skills`、`media_creation` 才递归包含子目录。
	- 备份包内的普通文件条目不保留源文件的 POSIX 权限与属主信息，统一按条目名以普通文件（0644）写入；恢复解包时本来也不回写目标权限。恢复时直接流式解析 TAR。由于 Android 环境不保证支持硬链接，打包时写入的 TAR 硬链接条目会在目标条目落盘后于暂存目录展开成独立副本（复制内容），不再创建硬链接。
	- 恢复时若存档包含非空 `upload`，会在应用阶段把原 `filesDir/upload` 整体移到 `pending/originals-upload` 备份，再用存档里的 `upload` 整体替换；恢复失败回滚时删掉新目录并把备份放回。存档没有 `upload`（或为空）时不动本地目录。
	- 导入时先读存档数据库声明的 schema 版本（`PRAGMA user_version`）：旧库（< 100）把 `upload` 里的每个文件都按内容重新算 sha256 并重命名为 `upload/<sha256>`（相同内容去重），把消息与设置里的旧文件名改写为 sha256，再把旧 `managed_files` 表转成 `managed_files_cas`；已是 CAS schema（100 及以上）的存档完全不对 `upload` 做迁移，文件名与登记表保持原样。
	- 本地、WebDAV 和 S3 使用相同的新格式。
